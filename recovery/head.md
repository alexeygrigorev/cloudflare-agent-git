# Principal recovery of a head

The principal owns head recovery. Restore the existing project owner and its useful work, then let it replenish and supervise its team. Root restores an unavailable principal first and hands head recovery back to it. This guide uses the shared fencing, admission and saved-conversation procedure in [principal recovery](principal.md#restore-the-principal).

## 1. Establish custody and inspect the actual failure

Resolve the head's current native tag, full session ID, saved conversation, project workspace and team from the catalog, bus handoffs and project tracker. Inspect exact actor status, transcript binding, worker/workload processes and containment. Check for a newer owner before acting. A missed reply, stale label or failed SSH connection does not prove vacancy.

Preserve healthy workers, reviewers, pending reviews, source claims, private logs and launcher tasks. A head can be quota-held, busy or protecting a draft while its workers remain useful. Send one native sync request and inspect the failing transition rather than repeatedly injecting reminders. Recovery must not interrupt productive work or promote an executor into the head role without custody.

## 2. Delegate independent recovery work

Reuse the maintained recovery team. Launch scoped recovery agents through the Agent Quota Launcher for independent diagnosis or tooling repairs; the principal supervises milestones rather than every tool call. Each task names an owner, affected actor, exclusive scope, permitted bounded actions, vacancy fence when applicable, expected artifact, checkpoint, different-model acceptance owner and continuation trigger. Record genuine first action and incremental results.

Run separate head recoveries and disjoint repairs in parallel when fresh capacity permits. Serialize actions on the same actor, conversation, lease, canonical store or integration boundary. Product implementation and code review stay with the project head's team. An unavailable head cannot repair itself; restore its interactive owner using the procedure below while delegated repairs continue.

## 3. Resume the head independently

1. Prove the saved conversation has no live writer, or obtain an acknowledged handoff and supported exit, then verify the old writer is gone. Preserve the old record and reconstruct missing context from the project's instructions, tracker, bus and founder journal. Never invent a saved conversation ID.
2. Discover the installed provider's resume flags and fresh admission route. Prefer the maintained launcher's accepted interactive role route. A headless executor route is not a head route. When that route is unavailable, use the bounded native bootstrap in [principal recovery](principal.md#bounded-bootstrap) with the verified head tag, provider, saved conversation and workspace. Read the workspace's own `AGENTS.md`; do not assume every head lives in the competition repository.
3. Launch through an independent SSH login to the host, or a supported manager that places both the PTY worker and model workload outside the principal's containment. From the principal, an authenticated self-SSH login can provide this boundary; discover its configured alias and verify actual placement. Do not run `aplexer start` directly inside the principal workload merely because the model appears in a sibling cgroup. This bootstrap is an interactive head recovery, not a hand-launched headless worker.
4. Check both worker and workload ancestry, login session and cgroups. The head and its future workers must survive the principal exiting and retain their own resource limits. Do not raise limits or move a live worker blindly. If an already productive head is nested, arrange its acknowledged checkpoint and supported exit, verify the exact writer is gone, then resume that same conversation once through the independent route.
5. Require native `whoami`, a bus custody ACK to the principal, an actual useful tool or artifact, and the next checkpoint. Verify the saved goal state. An active `Pursuing goal` requires no new `/goal`; if inactive, deliver a goal through supported native control only at a verified idle, empty prompt. Busy, menu, draft, quota-held and unknown states are protected. Retain a failed envelope and repair supported delivery rather than spoofing readiness.

## 4. Verify resumed project work

Ask the head to reconcile its existing launcher tasks, executor/reviewer identities, claims and review candidates before launching more workers. Verify one priority task resumes with an actual first action and incremental output; a PID, goal or queued launch is insufficient. The head chooses ready work, arranges different-model review on the exact result, integrates accepted work and starts the next useful task.

Record the diagnosis, executed action, new custody, private evidence references, independently accepted result, original missed checkpoint, next owner/action/due time and durable continuation trigger in the existing project issue. Report sanitized outcomes to root. Keep incomplete launcher, rearming and death-recovery acceptance open in [issue 102](https://github.com/alexeygrigorev/cloudflare-agent-git/issues/102); a recovered head does not establish an installed guardian.

If a route fails, preserve its exact request and inspect quota, tool permissions, provider routing, native readiness and placement. Use a freshly admitted healthy alternative for separate ready work while a named owner repairs the failing route. Preserve the existing conversation; provider failover must not create competing writers. A blocker report alone is not completed recovery.
