## A. Verified platform facts that constrain every approach

- A1. **Billing starts Oct 14 per pricing docs** (E-RZ108), vs Oct 15 in the blog (E-C008/E-C311). This resolves Codex's outstanding "confirm pricing discrepancy" — it is real; treat docs as authoritative. Practical effect: the contest window ends the day billing starts; demo cost is trivially inside the included tier (10k ops, 1 GB), but the **Workers Paid account is a hard dependency of any live demo** and nobody has one assigned yet.
- A2. **No merge, branch-CRUD, diff, or PR API; events are post-hoc** (E-RZ102/105/107; matches E-C305/308). Consequence: nothing in the platform can *prevent* a bad push. Every enforcement story collapses into exactly three shapes: (a) advisory pre-edit claims (bypassable, E-X012), (b) a trusted publisher holding the only canonical write token (Codex's design), (c) post-hoc revert (undo ledger). Approaches that imply pre-push enforcement without one of these are selling something the platform cannot enforce.
- A3. **Push is git protocol v1 only, no partial clone (`filter`)** (E-RZ103, matches E-C307). Standard git CLI is fine; agent harnesses built on libgit2/isomorphic-git wrappers are unproven against v1 receive-pack. MVP should mandate plain git + tokens.
- A4. **Blog (2026-04-16) advertises native git notes** (E-C302) **but no notes method appears in today's binding/REST docs** (E-RZ101/102). Notes remain usable via plain git (they're refs), but any provenance approach must not assume binding/API support for metadata.
- A5. **The "read" token scope also covers "indexing, review"** (E-RZ107 wording) and Cloudflare's co-author says the git interface is not the end goal of an "agent first VCS" (E-C316). Cloudflare is likely to ship agent-native semantics (indexing/review/merge?) mid-competition. Anything that is a thin wrapper on Artifacts primitives gets absorbed; novelty must live in the layer above (multi-agent policy, arbitration, economics), not in exposing the primitives.
- A6. **Cloudflare dogfoods session-as-repo + fork** (E-C303) and best practices prescribe repo-per-unit-of-work (E-C309). Judges work at Cloudflare: "we give every agent a repo" is the platform's own pitch, worth zero originality points. Isolation is table stakes; the differentiator is what happens when the forks meet.

Weakest fit of the 22 — demand a falsification test that a maintainer would actually run it.

## C. Strongest rejection of Codex's preferred candidate (bounded intent reapplication + exact-SHA receipt + human approval), as requested

1. **The unpriced runner gap.** Receipts must record "tests actually ran and passed" — but Workers cannot execute an arbitrary project's test suite. That requires Cloudflare Sandboxes/containers (new dependency, new cost, new latency) or local runners (breaks the server-side arbitration story). Every failure mode Codex lists (fake receipts, removed tests, stale evidence) is only detectable if the trusted runner actually exists. This is the load-bearing component and it has no spike scheduled yet. If the runner spike slips, the candidate degrades to "merge queue with JSON."
2. **Reapplication is the least deterministic component in a live demo.** A re-derivation on stage can produce a third, different diff (model nondeterminism), silently widen scope, or burn minutes of model time on beta APIs. The 5-10 minute video is unforgiving of "the agent is thinking." Mitigation exists (pre-recorded fallback = honest but weaker; bounded retry = visible cost) but nobody has demoed the failure path.
3. **Merge-queue resemblance is fatal at 50% originality unless the demo proves the delta.** Reject-stale-and-retest is what GitHub merge queue already does (E-C341). The genuinely novel claims — intent-aware recovery and tamper-evident receipts — are exactly the parts most likely to be hand-waved in the video. If the demo can't show a *fake receipt being rejected* and a *stale approval being denied* live, judges will pattern-match to a queue.
4. **Human approval on every publish cuts against the 25% multi-agent-effectiveness axis** (autonomy/coordination visible) even as it serves the review sub-criterion. Needs a policy knob (auto-publish to sandbox repos, human gate only for canonical) or the demo reads as human-bottlenecked.
Verdict: not fatal — reject the framing, keep the mechanism, gate it on runner spike #1 within ~48h. Note for the debate: this candidate and Claude's unmet-need-#1 "integration engine" (continuous trial merges + early conflict notification + landing order) are converging on the same product from two sides; the shortlist must not spend two of six slots on them without an explicit differentiation between notification-first and receipt-first.

## D. What both principals currently miss

- D1. **The judging text says "prototype for agent-oriented software collaboration."** Both current favorites are human-dashboard-heavy. The 50% axis likely rewards an agent-facing API surface (query integration status, claim paths, receive conflict notices, submit receipts — machine-first), with the dashboard as the demo wrapper. Neither seed makes the agent the primary UI.
- D2. **Demo/logistics critical path is unowned**: Workers Paid account + Artifacts namespace + US/Canada-eligible entrant decision (E-RZ206) + who submits. These are orchestrator decisions due early; research progress cannot substitute for them.
- D3. **The burden is beating "good enough."** Multiple practitioners report plain worktrees + personal review already work (E-C315, E-C325, E-C352, E-C361) and skeptics ask why not GitHub+worktrees (E-C314). Every shortlisted approach needs an explicit "why plain worktrees + a merge queue lose" falsification test, or it is a solution shopping for a problem.
- D4. **Self-reported benchmarks are load-bearing in two places** (weave 31/31, AgentFS) — both flagged by peers but still drifting into synthesis language. Treat entity-merge as unproven until a 2-fixture spike runs; do not let a shortlist slot depend on it.
- D5. **Bounded compute.** Five heads × ZCode teams × parallel agent forks is the experiment's stated design, but nothing bounds model spend per lane. Recommend the orchestrator set a per-lane budget at consensus time; unbounded reapplication loops are the specific failure mode (C2).
