## 2. Artifacts capability matrix as recorded from the inspected docs pages

Sources: developers.cloudflare.com/artifacts/api/workers-binding/, /artifacts/api/rest-api/, /artifacts/api/git-protocol/, /artifacts/guides/authentication/, /artifacts/platform/limits/, /artifacts/guides/event-subscriptions/, /artifacts/concepts/best-practices/, /artifacts/concepts/how-artifacts-works/, /artifacts/examples/sandbox-sdk-artifacts/, /artifacts/examples/isomorphic-git/, /workers/ci-cd/builds/git-integration/artifacts-integration/, /workers/previews/. Recorded [R] from the listed pages — fetch verification lost, not independently re-verified; specifics marked [X] are cross-verified against Codex's recorded fetches. Capability statements hold for the inspected pages only; absence claims below are doc-absence, not proven API-absence.

**Control plane (Workers binding `env.ARTIFACTS` / REST):**
- `create(name, {readOnly, description, setDefaultBranch})` → returns `{name, remote, defaultBranch, token}` — token returned **once** at creation.
- `import({source:{url,branch,depth}, target:{...}})` (async; 409 while importing), `fork(name, {defaultBranchOnly, readOnly, description})` (status `forking`), `get(name)`, `list({limit,cursor})`, `delete(name)` (REST returns 202).
- Per repo: `info()`, `log({ref, limit≤1000, offset})` — **first-parent chain only**, `readCommit(hash)`, `readTree(hash)` — **immediate children only**, `readBlob(40-char SHA-1)`, `readFile({ref, path})`.
- Tokens: `createToken(scope "read"|"write", ttl)` (REST: ttl 60s–365d, default 24h), `listTokens`, `revokeToken`. Scope granularity is **repo-level only** — no branch/path/ref scoping exists.
- **The inspected binding/REST pages document no method for: clone, fetch, push, merge, branch listing, ref listing, diff, tags.** This is absence in the inspected docs, not proven API-absence. Repo content access is read-only except through the Git protocol per those pages.

**Data plane (Git over HTTPS):**
- Remote: `https://<ACCOUNT_ID>.artifacts.cloudflare.net/git/<namespace>/<repo>.git`.
- Auth: repo-scoped token `art_v1_<40hex>?expires=<unix>`; Bearer header (`http.extraHeader`) or basic-auth URL (secret only in password slot).
- upload-pack (clone/fetch): protocol v1+v2 documented; v1 supports **shallow/deepen**; missing `filter`/`include-tag` are documented among optional **v1** capabilities — a v1-scoped statement, not proof that v2 fetch lacks filtering. Artifacts v2 capability negotiation is untested [U]; the ArtifactFS guide documents on-demand blobless hydration on Artifacts, with documented eager fallback when the server advertises no filtering [X: E-X021, research/codex/pro-integration-round-1.md]. Never budget blobless savings without measurement.
- receive-pack (push): **v1 only** (no v2 push).
- Rate limits: control plane 2,000 req/10s per namespace; Git 2,000 req/10s per repo. Limits: **1 GB/repo, 32 MB/file-or-blob, 1 TB/account**, unlimited repos and namespaces.

**Events:** Cloudflare Queues event subscriptions (`npx wrangler queues subscription create … --source … --events …`). Account-level: `repo.created/deleted/forked/imported`. Repo-level: `pushed` (payload: `ref`, `before`/`after`, commits array with `commitsTruncated` flag), `cloned`, `fetched`, `token.created/revoked`. Queues delivery is **at-least-once, no ordering guarantee** [X: research/codex/engineering-feasibility.md]; retries 100, consumer concurrency 250, 15-min consumer wall clock [R: queues/platform/limits, queues/reference/how-queues-works].

**Execution substrate for agents:** Sandbox SDK (`@cloudflare/sandbox`, Workers Paid) — Containers (per-instance microVM, Durable Object scheduling, can host real coding agents "such as Claude Code, Codex, and Devin") and Dynamic Workers (isolated JS/Python/WASM). Official example `git-repo-per-sandbox`: one repo + one sandbox sharing an ID; inject authenticated remote as env var; short-lived (3600s) write tokens. **[R]**

**Git-in-Worker without a sandbox:** isomorphic-git over in-memory FS: `init/add/commit/push` from inside a Worker (official example). Suited to "a short-lived working tree in memory". **[R]**

**CI/publishing:** Workers Builds can connect an Artifacts repo; **production branch is `main` only**; other branches build **Previews** (must be enabled; default preview command `npx wrangler preview`); "Preview URLs are public by default. Use Cloudflare Access to require sign-in" (protectable per account/Worker/hostname); limits 100 previews/Worker (Free) / 500 (Paid), 100 deployments/preview, **oldest auto-deleted** at cap. **[R]**

**Architecture:** each repo is "an isolated Git service" routed like a Durable Object; sync replication across DCs + async to object storage; repos persist until deleted. **[R]**

**Cloudflare's own recommended pattern (best-practices):** "If you have 10,000 agents, create 10,000 repos"; "Use branches only when collaborators share the same lifecycle"; don't use a shared repo as an agent queue; fork from a trusted baseline; per-session short-lived tokens ("mint the narrowest token you can, for the shortest time you can"); **use git notes (refs/notes/*) to attach prompts/model output/run IDs to commits** — and remember to push/fetch notes refs; shard namespaces to stay under per-namespace rate limits. **[R]**

## 3. Feasibility verdicts per requested area

### 3.1 Concurrent-agent branch isolation — FEASIBLE, with a design choice forced
- **[R]** Multiple agents can hold read/write tokens and clone/fetch/push concurrently; Git endpoint tolerates 2,000 req/10s per repo; Sandboxes give each agent an isolated microVM; repo-per-sandbox is an official template.
- **[R]** Cloudflare explicitly steers away from N agents pushing branches into one shared repo ("10,000 repos" guidance). Branch-per-agent in a shared repo is *possible* (push `HEAD:refs/heads/agent/x` is ordinary receive-pack) but is contrary to published best practice.
- **[U]** No branch listing API: neither binding nor REST exposes refs. Discovering sibling agent branches requires `git ls-remote` with a read token (protocol v2 `ls-refs` is supported) or replaying `pushed` events.
- **[P]** Recommended isolation model: **fork-per-agent from a trusted baseline** (binding `fork`, `defaultBranchOnly: true`), each agent pushes only to its own repo; the platform mediates everything else. This aligns with official best practice and makes isolation structural rather than disciplinary.
- **[P]** If branch-per-agent in one repo is desired for demo optics, it works, but the platform must mint write tokens per agent and must never share them — tokens are repo-wide, so any agent holding one can overwrite any branch including `main` (see failure-cases #1).

### 3.2 Stale-base integration — FEASIBLE, but there is NO server-side merge; the platform is the merger
- **[R]** No merge endpoint exists anywhere in binding or REST; merging is done by Git clients. No PR/merge-request object, no diff API, no conflict-detection API.
- **[R]** Forks "start from the source's history, then diverge independently"; nothing auto-syncs a fork with its base. `before`/`after` SHAs in `pushed` events let the platform know what each side changed.
- **[P]** Integration worker design: on proposal submission, clone/fetch baseline + proposal (isomorphic-git in a Worker for small repos, or a Sandbox for real `git merge`), compute merge-base, attempt three-way merge, run tests, then fast-forward-push the baseline `main` via a platform-held write token. Serialize per baseline with a Durable Object lock so two integrators can't race `main` (artifacts pushes to one repo route to one logical instance, but our read-modify-write cycle is NOT atomic — the lock is mandatory, see failure-cases #2).
- **[P]** Staleness policy: proposals record their merge-base; if `main` advanced, integrator rebases/merges baseline into the proposal branch first, re-runs tests, and only then merges back. Receipt records old vs new base.
- **[P] Publication fence (required — DO serialization alone is NOT sufficient):** a DO lock prevents two publishers racing, but it does nothing about (a) a stale canonical head (test ran at X, head already at Y), or (b) a stale writer — e.g., an integrator that crashed, lost its lease, and wakes up later still holding a canonical write token. The fence must be: the canonical write token is held ONLY by the publisher path; before every push the publisher re-reads the remote head (`ls-remote`/fetch); the push must be a **non-force fast-forward update from the exact tested merged SHA**; if the head moved, the approval is stale → reject and re-integrate. The fence also requires the publisher to present a **current publisher lease/generation and the currently approved policy version**: a publisher whose lease expired (crash → wake-up) or whose generation/policy is superseded is rejected **even when canonical HEAD has not moved** — a head re-check plus non-force push is not lease authorization. This fence works only if Artifacts receive-pack rejects non-fast-forward ref updates — undocumented [U], spike item 1. If non-FF pushes turn out to be accepted, the FF fence fails; keeping the canonical repo `readOnly` and publishing by replacement/import is an **unresolved contingency — not implemented, not validated, changes repository identity, and requires a stable publication contract that has not been designed** [P].
- **[U]** Force-push behavior on Artifacts (allowed? rejected?) is undocumented; it decides both whether the fence above holds and whether integrators can maintain long-lived `integration/*` branches. Treat non-fast-forward pushes as rejects and always merge forward until spiked.

### 3.3 Provenance receipts tied to commit+tests — FEASIBLE and officially endorsed via git notes
- **[R]** Best-practices page explicitly recommends git notes for "prompts, model output, and run IDs" attached to commits, with the caveat to push/fetch `refs/notes/*`.
- `pushed` events deliver after-SHA + commit metadata (with truncation flag) — the trigger for receipt generation; `token.created/revoked` events let us record *who* had write access when [R]. Queues is at-least-once/unordered [X] → **event-delivery deduplication** is required and is distinct from receipt identity (next point). The dedup key must include the publisher generation and the policy digest and must be invalidated when either changes, so a notice re-emitted for a new generation or policy is never suppressed as a duplicate. Receipts are ordered by Git ancestry (parent links, `before`/`after` chains), never by event timestamps or arrival — timestamps are display hints only.
- **[P]** Receipt content and identity: a receipt attests that **a specific runner, in a specific environment, ran a specific accepted policy version over a specific tree and observed a specific result — it attests a runner result, NOT correctness of the code.** Receipt identity tuple (all fields required): `{canonicalRepo, baseSha, candidateSha, mergedSha, mergedTreeHash, testPolicyVersion + policyCommitSha (pins the exact test content, not just a label) + policyDigest, oracleDigest (identity of the independent oracle), environmentDigest, runnerIdentity, attemptId, generation (see ordering below), result: {cmd, exit, sanitizedOutputDigest, logRef}}`. Do NOT key receipts on `(repoId, afterSha)` alone — that collides across attempts, generations and policy versions. Deduplicate repeated *event deliveries* separately (previous point); the receipt itself is identified by the full tuple.
- **[P] Receipt/policy/generation ordering:** integrations form generations — the merged tree of generation k is the base of generation k+1. Receipts are append-only, chained by `parentReceiptId`, and validated against Git ancestry of `mergedSha` (a receipt whose `baseSha` is not the canonical-head ancestry at publish time is stale → invalid). A receipt is valid only under the policy version/commit approved for its generation; policy versions are monotonic, human-approved, and results are never compared across policy versions. D1 ledger rows are never rewritten — a correction is a new attempt with a new `attemptId`; the ledger orders receipts by Git ancestry, timestamps for display only.
- **[P] Policy ownership and independent oracle:** the acceptance policy (tests/checks) lives on the approved baseline and is versioned; a candidate can NEVER pass by altering or choosing its own tests. The verdict is computed only by the platform-owned runner executing the baseline-owned policy — the **independent oracle**; candidate-emitted results are untrusted claims (FC-5/FC-11). The oracle itself is versioned and pinned by digest in every receipt; comparative arms (comparative-spike-plan §4) must use the identical oracle and identical acceptance checks. Policy evolution for intended API changes (e.g., approved contract migrations) requires explicit human approval and bumps the policy version recorded in subsequent receipts (matches the approved-contract-change scenario in research/codex/local-validation.md).
- **[R]** Test execution substrate: Sandbox containers can run arbitrary commands (real test suites) and host real coding agents; consumer wall clock 15 min / CPU 5 min via Queues; Workflows can orchestrate longer.
- **[U]** Whether git notes survive forks (`defaultBranchOnly` forks presumably drop notes refs) — unknown; anchor receipts on the baseline repo, not agent forks.

### 3.4 Permission-scoped publishing — PARTIALLY FEASIBLE; enforcement must be app-layer
- **[R]** Token scoping stops at repo+read/write. There are no branch, path, or environment scopes. An agent with a write token can push any ref in that repo (branches, notes, tags — if accepted by receive-pack).
- **[R]** Structural mitigation is officially endorsed: repo-per-agent + per-session short-lived tokens + read tokens for everyone else; write tokens minted only after the Worker authorizes the session.
- **[R]** Preview publishing: branch previews exist (Workers Builds) but are **public by default**; Cloudflare Access can protect per account/Worker/hostname; previews are LRU-evicted at 100/500.
- **[P]** Scope model for the MVP: identity → session → **fork** (repo-scoped write, TTL ≤ 1h) ; read tokens for integrators/reviewers; publishing gated behind a platform endpoint that merges to `main` only after receipt verdict = pass; demo previews protected with Cloudflare Access (free tier supports this) or served only through the platform Worker with its own auth. What we *cannot* do is make Artifacts itself enforce branch-level permissions — say so explicitly in the demo narrative.
- **[U]** Whether Access-protected preview URLs can be minted per-branch programmatically for judge/agent-role separation — untested.

### 3.5 Durable handoff/context — FEASIBLE; Artifacts stores context, the platform must make it usable
- **[R]** Blog positions Artifacts for "storing work context alongside code" and repos "per project, user, session, or task"; best-practices endorses git notes for agent metadata; events (`repo.forked/imported/pushed`) provide handoff triggers; DOs/D1/KV available for coordination state; Sandboxes snapshot-restore files.
- **[P]** Handoff record: a `session/*` context file + git note chain in the session repo: goal, plan, decisions, open threads, env, next steps; handoff = fork of the session repo (fork is the official "continue from baseline" primitive) with a handoff note on the tip commit. DO keeps live coordination (task board, locks); repo keeps durable truth.
- **[U]** Size limits for notes (blob cap 32 MB applies) — keep notes small; **[R]** `log()` is first-parent only, so note-history walks need explicit notes-ref fetching, not `log()`.

## 4. Undocumented assumptions we are relying on (test before prototype)
1. Non-fast-forward and force-push behavior of receive-pack (standard-git rejection presumed, not documented).
2. Branch creation via `git push origin HEAD:refs/heads/x` (standard v1 receive-pack presumed).
3. `git ls-remote` and shallow clone against Artifacts remotes (v2 `ls-refs` + v1 shallow documented as supported; combined flows untested).
4. Whether `refs/notes/*` pushes are accepted (best-practices implies yes).
5. Whether fork copies all refs or only the default branch when `defaultBranchOnly` is unset; tag behavior.
6. Per-request memory behavior of isomorphic-git in Workers isolates for repos near the 1 GB cap (docs only bless "short-lived working tree in memory").
7. Queues event schema stability during beta (schemaVersion 1 today).
8. Exact billing-start date (pricing page Oct 14 vs blog Oct 15).
9. Preview build behavior for non-`main` branches of an Artifacts-connected repo under concurrent pushes (build queue semantics undocumented).

## 5. Recommendation
Feasible overall with app-layer enforcement: **fork-per-agent + fenced publisher (canonical token held only by the publisher; head re-check + non-force fast-forward) + git-notes/D1 receipts carrying the full identity tuple + Access-gated previews**. However, I no longer claim "no undocumented dependence": the critical path still leans on four unresolved unknowns — force-push/non-FF semantics (the fence is void if non-FF pushes are accepted), ref listing via `ls-remote` in practice, `refs/notes/*` acceptance and fork survival, and real-world event-delivery semantics. Each has a mitigation if the spike answers badly (D1-only receipts; event-replay branch discovery). The readOnly-canonical replacement contingency is not a working fallback — unimplemented, repository-identity-changing, dependent on an undesigned publication contract (§3.2). Each unknown must be spiked before any prototype (failure-cases.md §Top unknowns). Riskiest area remains stale-base integration. Comparative option analysis and executable spike plans: `comparative-spike-plan.md`; smallest MVP: `mvp.md`; adversarial cases: `failure-cases.md`.
