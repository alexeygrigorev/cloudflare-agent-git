## 1. Hard constraints that shape the comparison

1. **v1 partial-clone filtering is documented unsupported; v2/ArtifactFS behavior is unresolved.** The Artifacts Git protocol page lists missing `filter`/`include-tag` among optional **v1** capabilities, with v1 receive-pack and v1/v2 fetch [X: research/codex/engineering-feasibility.md §Documented boundary → https://developers.cloudflare.com/artifacts/api/git-protocol/ ; also recorded [R] in my feasibility.md §2]. This is a v1-scoped statement, NOT proof that v2 fetch lacks filtering: Artifacts v2 capability negotiation has not been tested, and the ArtifactFS guide documents on-demand blobless hydration on Artifacts with eager fallback when the server advertises no filtering [X: E-X021, research/codex/pro-integration-round-1.md]. Corrected consequence: **no blobless/lazy architecture may be assumed or budgeted against Artifacts remotes without measuring actual v2/ArtifactFS behavior** (eager-fallback risk); blobless clones from non-Artifacts origins (e.g., upstream GitHub) remain untested-but-standard. Other recorded on-demand read path: binding `readFile`/`readTree` (immediate children only) [R]. Sparse checkout remains a legitimate existing control regardless.
2. **Sparse checkout is not zero checkout.** Sparse-checkout still clones the object DB (full, given constraint 1) and materializes the selected tree; it only trims checked-out source bytes. Codex's synthetic measurement: 75% source-byte saving but only ~18.75% of total workspace bytes when simulated deps/build outputs dominate [M: research/codex/storage-validation.md]. Source-only optimization under-delivers; dependencies and build outputs are the real bytes.
3. **Remote Sandboxes move allocation; they do not eliminate it.** Container minutes, Artifacts storage/ops, and egress for logs/UI viewing shift to Cloudflare; total cost is not zero and is not provably "1× local" for all logs/caches [P — bounded only by billing-start facts: usage billing from Oct 15 per announcement E-X016 [X]; pricing page says Oct 14 [R] — unresolved, keep explicit]. Cost statements in this file are therefore structural, never numeric.
4. **Scale/size limits**: 1 GB/repo, 32 MB/blob [X: engineering-feasibility.md → limits page]. Events are post-hoc (no pre-push enforcement) [X: same]. Tokens are repo-scoped read/write only [R].
5. **Concurrency claims require real agents**: any "concurrent" demonstration below uses ≥2 actually running coding-agent CLI processes, not scripts (user correction; FC-9).

## 4. A03 comparison plan — repair-on-red-tree vs fresh-base reapplication (identical accepted policy)

Question: when a candidate breaks the combined state, is bounded repair of the red merged tree as good as re-running the task contract on a fresh base — or does reapplication earn its complexity?

- **Common setup**: the deterministic synthetic fixture (merge-fixture.py contract case) as the versioned task contract; acceptance suite = baseline-owned policy vN; candidates can never alter or choose the policy (FC-11); human-approved policy bump only for intended API changes, with the bump recorded. Same agent CLI + model config + retry budget (≤2) for both arms; register identical task/oracle/model/budget conditions BEFORE running; alternate arm order; distinguish active agent time from elapsed time; any third independent agent is budgeted through an already acknowledged head (≤2 new executors per head remains policy). The identical **independent oracle** and identical acceptance checks apply to both arms — extra tests or warning-compliance prompts must not favor either arm. N ≥ 5 runs per arm to expose nondeterminism (recorded concern E-A002/X5); raw per-run records preserved.
- **Arm R (repair-on-red)**: give the agent the red merged tree; instruct in-place repair under policy vN; constrain changed paths to the candidate-touched set.
- **Arm B (reapply-fresh)**: give the agent the original versioned task contract on the fresh base in a new fork, same policy vN; diff scope against the first attempt (scope-drift detection per Codex X5).
- **Metrics (no cost figures)**: pass-under-vN rate; scope drift (changed-path diff vs original attempt); wall time per arm; diff size; policy violations; every trial produces a receipt with the full identity tuple {base, candidate, merged SHAs, merged tree, policyVersion + policyCommitSha, oracleDigest, environmentDigest, runnerIdentity, attemptId, generation}. Token/compute spend is reported as "unknown" — this plan deliberately contains no token-cost numbers.
- **Interpretation**: no observed difference between arms on pass/drift/time → reapplication shows **no observed benefit in that sample** (five small stochastic trials cannot establish statistical equivalence; a tie is only "no observed benefit in this sample"); keep A03 as a feature candidate (matches A03 falsification in approaches-20.md). Arm R leaks scope or violates policy more often → the reapplication loop is the differentiator. Wall-time medians >15 min per loop → A03 fails its own product bar regardless.
- Deliverable: `spike-s3-a03-arms.md` (incremental, per-run raw records preserved).

### 6.2 A01 uptake-protocol clarifications — my independent critique (my file only; the owner's protocol file is not edited by me)

Context: research/zcode/independent/a01-uptake-protocol.md (rev2, unfinished-WIP basis) and the three clarifications the Codex principal requested (recorded in research/debate/codex-interactive-consultation-response.md).

1. **Dedup vs generation/policy (clarification 1) — endorse, with an operational addendum.** Dedup state must be keyed (head, notice kind, generation, policyDigest) in durable state (DO/D1) so a restart can neither resurrect a suppressed notice nor suppress a re-emitted one; the scripted dry run must include a restart-and-re-emit case, otherwise the invalidation logic is untested bookkeeping.
2. **Count funnel (clarification 2) — endorse; pre-register definitions before the run.** "Eligible emitted" = notices actually produced for live unfinished heads (not potential conflicts); fix the prevention/recovery boundary by push time — a notice consumed after the agent began its final write counts as recovery, not prevention — or stratification becomes post-hoc and flatters the system. Report a denominator at every stage (emitted/delivered/consumed/ignored/malformed/stale/effective).
3. **Equal conditions before arms (clarification 3) — endorse; add sample-size honesty.** With ~5 runs per arm, order and variance dominate: alternate arm order, keep per-run raw records, and treat a tie as "no observed benefit in this sample," never equivalence (guidance-review point 4). Separate active agent time from Sandbox/queue elapsed time. The ≤60 s push-to-warning figure circulating in debate is a **target, not a measured achievement**.
4. **Warning-while-unfinished interplay (principal Q3 position).** Uptake should be measured as behavioral adjustment against the completion-time comparator (did the agent change course), not merely notice consumption; the unfinished-WIP basis (rev2) is correct — completed-change oracle recovery is not live WIP uptake (R5-2, accepted).
5. **Boundary.** These critiques live only in my file. A scripted dry run validates bookkeeping only: no uptake, latency or agent result is claimed, and no part of the protocol has been executed by me.
