Scope: all 11 book action checklists; relevant current experiment AGENTS.md and principal coordination notes. ## What the repository actually establishes

`learning/book-action-checklists/README.md:3` calls these source-linked, summary-based practical reconstructions, not official workbooks. The files describe reading/listening companions and have unchecked tasks. Their presence does **not** verify completed reading, personal adoption, or agreement with every recommendation. All 11 titles appear in README lines7–17: The Mom Test, Hooked, The Lean Product Playbook, Obviously Awesome, Superfans, The Minimalist Entrepreneur, Company of One, The SaaS Playbook, Zero to Sold, The E-Myth Revisited, Million Dollar Weekend.

The experiment currently has five retained hypotheses, A14 folded into A01 verification and slot six open. There is no final six-approach sign-off. Current engineering tests include an unequal-policy real-agent pilot, synthetic storage fixtures, and actual aplexer binding recovery. Those have different evidential meanings. Methods below should improve those ongoing lanes, not add another project or substitute book authority for outcome evidence.

## Highest-priority applications

### 1. The Mom Test: demand evidence independent of technical proof

Repository locators: `the-mom-test.md:13–26` (past experiences/workarounds), `:33–39` (compliments and hypothetical promises), `:55–73` (overturnable assumptions; demand versus delivery risk), `:90–105` (concrete commitments), `:136–148` (segment and buying group), `:170–177` (decisions and continued contact).

Adopt now: every project head keeps a short demand section separate from its engineering section. Ask practitioners about their last concurrent-agent integration failure or last disk-full worktree incident: what happened, what they did, time/disk/code lost, frequency, and which existing tool they tried. Public Reddit/HN posts supply leads and symptoms; they do not establish purchasing authority or willingness to change workflow.

One-week test, proposed experimental targets rather than book rules: identify five relevant practitioners across two segments; draft interview questions now, with actual outreach only under appropriate explicit messaging authorization. Seek at least two concrete commitments to run an isolated workflow trial on a real task, rather than collect positive reactions. Record refusals and workarounds. If no one can identify a recent consequential incident, narrow or park that segment rather than argue the problem should matter.

For the storage lane, the user is already one real participant. His host measurement is valuable. It is a sample of one and should not be renamed broad market validation. For A01, ask about the consequence of semantic integration failures, not whether people like warning dashboards. User and buyer may differ in team environments.

### 2. The Lean Product Playbook: one unsupported hypothesis, one useful test

Locators: `the-lean-product-playbook.md:13–22`, `:38–52`, `:56–73`, `:89–108`, `:142–145`.

Adopt now: each lane defines (a) exact user, (b) outcome, (c) current alternative, (d) differentiating benefit, (e) weakest assumption, (f) one test that could reject it. Select the cheapest appropriate fidelity: a concierge report for a workspace diagnosis, real concurrent writers for A01 correctness, a genuine restart/reply trial for aplexer. A homepage or mockup cannot settle data isolation; a benchmark cannot settle demand.

One-week tests: workspace-doctor produces a read-only recommendation on an actual workspace and measures whether the owner can act on it safely; no deletion of existing trees. A01 runs the already-planned matched-policy task/oracle trial, preserving candidates until independent replay. Aplexer asks a fresh operator to perform a real handoff/resume without root rescue. Count goal completion and failure recovery separately from successful transport or screen activity. Predeclare desired minimum benefit and stop conditions; do not use generated fixtures or base-code refusal as proof the intended work was completed.

Important caution from `:22`: our own usage may not represent intended customers. Dogfooding is excellent product-risk evidence and a source of failures. It is not product-market fit.

### 3. Obviously Awesome: compete with the actual workaround

Locators: `obviously-awesome.md:24–29` (scope, champion, hypothesis), `:58–65` (actual alternatives, including doing nothing), `:71–90` (specific evidenced differences and outcomes), `:110–117` (category choices), `:145–149` (live testing).

Adopt now: position each useful slice independently instead of calling everything a new Git platform. Candidate descriptions to test:

- Workspace doctor: identify and reduce repeated dependency/build storage while preserving writable source isolation. Alternatives include current package caches, existing environment sharing, sparse workspaces, and tolerating disk growth.
- A01: complete overlapping agent changes without silently breaking combined behavior. Alternatives include ordinary Git plus tests, work ownership, serial integration, and incumbent agent-conflict warnings.
- Aplexer: a reliable cross-session/cross-computer task handoff, with durable identities and verified recovery. Alternatives include tmux, files, issue trackers, and manual checks.

One-week test: create a single page per lane listing current capabilities, proposed capabilities clearly labeled, real alternatives, champion and measured difference. Put it beside a live trial with a suitable practitioner; ask them to explain the tool and compare it to what they would otherwise do. Confusion about the category or no valued difference is a reason to revise. Do not claim novelty solely because a competitor's API or source access was unavailable.

### 4. The Minimalist Entrepreneur and Company of One: reduce organization before expanding it

Locators: `the-minimalist-entrepreneur.md:21–31`, `:35–45`; `company-of-one.md:22–27`, `:33–35`, `:76–82`, `:105–110`.

Adopt now: keep the five heads as exploratory ownership, not an obligation to create five standalone businesses or five large executor teams. Use manual, clearly owned workflows to establish one valuable result before automating them. Give specialists outcomes and freedom, then measure ongoing coordination burden. Ample tokens are available capacity, not a customer outcome.

One-week test: each head names one result it can deliver with existing tools, one user/task, and a maximum resource budget. Compare successful accepted outcomes with executor count, token use, disk growth and human intervention. Trial one simpler workflow against the current coordination process. Keep it only if it produces useful results with lower cost or better reliability. This fits the user's explicit workflow autonomy; no routine approval dependency is needed.

### 5. The E-Myth Revisited and Zero to Sold: standardize only proven improvements

Locators: `the-e-myth-revisited.md:59–68`, `:77–84`, `:126–129`, `:154–159`; `zero-to-sold.md:72–80`, `:87–88`, `:173–184`.

Adopt now: build the agent protocol by innovation → measurement → repeatable operation. Each rough edge gets an owner, reproduction, bounded patch, independent review, exercised recovery and an updated runbook. The orchestrator should not be required to manually unstick every peer. This reinforces the user's requested proactive rule with a testable operation model.

One-week test: aplexer owner and reviewer perform actual sender restart, receiver restart, duplicate/lost-receipt replay and resumed-tag routing, then have another head execute the documented procedure. Count delivery, reply threading, idempotent persistence and task continuation separately. Existing real two-computer SSH mailbox proof is useful, but does not establish a shipped native cross-host router. Add a reversible scoped integration after review; preserve the ordinary Git fallback and independent restoration evidence.

## Grounded challenges to the user's framing

1. **Twenty approaches and six finalists are portfolio scaffolding, not evidence of six opportunities.** Keep the sixth slot open unless a distinct need survives a test. Use book methods to learn which ideas should die, not generate an obligation to fill slots.
2. **Large agent capacity and five heads can increase coordination faster than progress.** Track accepted real-user outcomes per resource budget, not agents launched or research documents produced. Compare a simpler lane before adding teams.
3. **The observed disk pain may call for a dependency/workspace lifecycle tool before a new Git hosting platform.** Corrected host evidence puts dependency/build directories at 69.4 GiB of 111.7 GiB physical union (62.1%). That supports testing a narrower remedy; it does not prove existing worktrees are deletable or safely shareable. Compare isolated writable source with independently protected reusable dependencies in new small test trees.
4. **Internal dogfooding should start early but cannot validate external demand.** Use it to find integration and recovery bugs; separately seek practitioner task commitments and costly-problem evidence. Preserve that distinction in the experiment ledger.

## Minimal shared artifact

One evidence card per lane is sufficient: owner; user/champion; last concrete problem; current alternative; cost; hypothesis; discriminating test; protected acceptance check; minimum useful benefit; falsifier; next commitment; rollback/recovery; actual result and next decision. This consolidates the books into execution instead of adding 11 new checklists to the agents' workload.
