## 4. Deep-Dive on Systemd Behavior & Vulnerabilities

### 4.1 `--wait` Parent Scale Risks & Head Cgroup Saturation
The audit confirmed the reviewer's finding that the public launcher architecture cannot scale to 50 concurrent public-CLI launches:

- In `launcher/cli.py` (`run_task_units`), every launch invokes:
  ```python
  execute_transient_task_unit(..., wait=True)
  ```
- `spawn_transient_task_unit(..., wait=False)` exists in `task_units.py` but is **never invoked** by the public CLI.
- Because `execute_transient_task_unit` executes `systemd-run --wait` via `subprocess.Popen(..., start_new_session=True)` from within the controller head's environment:
  - The `python3 -m launcher` process and the `systemd-run --wait` process remain inside the head controller's cgroup (`aplexer-workload-6be4c247-4410-4bdb-968e-7fc2d5844941.scope`).
  - The head cgroup has a rigid limit: `TasksMax=100`.
  - While the worker payload itself executes inside an isolated sibling unit (`app.slice/agent-task-*.service`), the controller processes stay resident in the head scope for the entire task lifetime (e.g., 16 minutes for 1c).
- **Corroborating Evidence**:
  - The reviewer recorded `TasksCurrent=86/100` in the head cgroup with four in-flight sibling units.
  - The auditor discovered direct evidence of this saturation in `.local/launcher-config/state.db`:
    ```text
    task-ql-review-pub-1c | failed | [Errno 11] Resource temporarily unavailable | 2026-10-05 11:03:41
    ```
    This fork/clone failure (`EAGAIN`) occurred at 11:03:41Z when attempting to launch a task right before `task-ql-review-lifecycle-31b41e` was dispatched at 11:03:47Z, proving that thread/PID exhaustion in the head scope is a real, active failure mode.
  - A 50-wide concurrent launch wave would require at least 50 Python processes + 50 `systemd-run` processes = 100 PIDs, immediately violating `TasksMax=100` before accounting for shell and agent overhead.

### 4.2 Post-`--collect` Metadata Erasure and Property Default Hazards
The audit verified the exact property erasure behavior that occurs when `--collect` is passed to `systemd-run`:

- When a transient unit completes, `CollectMode=inactive-or-failed` causes systemd to unload the unit and destroy its cgroup directory.
- Running `systemctl --user show agent-task-*.service` on a collected unit yields:
  ```ini
  LoadState=not-found
  ActiveState=inactive
  SubState=dead
  InvocationID=
  ControlGroup=
  MainPID=0
  MemoryMax=infinity
  TasksMax=76970
  Result=success
  ```
- **Hazard 1: Phantom Resource Limits**: `MemoryMax=infinity` and `TasksMax=76970` are host-level fallback defaults for missing unit definitions, not the 768M / 100 constraints applied at launch. A roster or monitoring tool querying `systemctl show` after unit termination would misreport resource enforcement as unconstrained.
- **Hazard 2: Receipt `cgroup: ""`**: Because `verify_task_unit_cleanup` queries properties after `systemd-run --wait` returns and collect has executed, `props.get("ControlGroup", "")` is empty. Consequently, CLI receipts always store `"cgroup": ""`, meaning receipt JSON contains no cgroup isolation proof.
- **Hazard 3: Timeout-Kill Bypass**: In `launcher/task_units.py`:
  ```python
  except subprocess.TimeoutExpired:
      if assigned_inv_id:
          chk = subprocess.run(["systemctl", "--user", "show", unit_name, "-p", "InvocationID"], ...)
          curr_inv = ...
          if curr_inv and curr_inv == assigned_inv_id:
              subprocess.run(["systemctl", "--user", "kill", "--signal=SIGKILL", unit_name], ...)
  ```
  If `--collect` has already cleared `InvocationID` (`curr_inv == ""`), the condition `curr_inv and curr_inv == assigned_inv_id` evaluates to False, skipping the kill command entirely.
- **Hazard 4: Cleanup Verification Flaw**: In `verify_task_unit_cleanup`, when properties are empty, the code falls back to `_is_cgroup_dissolved_or_empty(f"app.slice/{unit_name}")`. Task `task-pub-history-filter-1b` failed because leftover artifacts or timing caused this check to return False with empty metadata:
  ```json
  {"error": "unit agent-task-task-pub-history-filter-1b.service did not cleanly dissolve lingering PIDs or cgroup: {'ExecMainPID': '0', 'ControlGroup': '', 'ActiveState': 'inactive', 'SubState': 'dead', 'InvocationID': ''}"}
  ```
  While `2b` and `1c` passed, the mechanism is prone to race conditions.

### 4.3 Floor-Admission Accounting Skew
The reviewer correctly noted a discrepancy between Store submission accounting and task execution:
- Tasks submitted via CLI record `task_resources.memory_mb = 1500` (default submission parameter).
- The unit is actually launched with `MemoryMax = 768M`.
- `run_task_units` in `cli.py` never calls `store.get_active_resources()` and calls `admit_task_unit` without passing `active_mem_mb` (defaulting to 0).
- As a result, concurrent starting siblings do not decrement available memory against one another during task admission.
