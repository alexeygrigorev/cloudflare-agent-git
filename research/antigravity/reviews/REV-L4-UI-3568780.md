## Verdict

**REQUEST_CHANGES**

Nothing in this commit is broken, and the outage downgrade genuinely works. The
request for changes is about **truthfulness of the change itself**: the guard the
commit message and the dispatch both name as the fix is provably dead code (the
requested negative test does not fail), and a green verified-clean badge is still
rendered during the very outage the commit says it suppresses. Both are cheap to
fix, and neither is caught by any test.

Concretely, do not read this as "the UI lies during outages". Read it as "the commit
claims a mechanism that does not exist, and the visual result does not match the
commit's own success criterion".

There is no separate `isFailureView` predicate; the failure view is simply

This is a dispatch-precision issue rather than a code defect, but it matters for the
verdict: the negative test the dispatch asked for was aimed at a construct that does

## F1 (Medium) — the named outage guard is dead code; the requested negative test does not fail

`prototype/ui/ui.js:631`:

```js
var matchesHead = !stale && (!currentHead || !ev.head || ev.head === currentHead);
```

`matchesHead` is read in exactly two places, and both are inside the **else** branch
of a `stale ? ... : ...` ternary:

- `prototype/ui/ui.js:644` — `(stale ? "(live status unconfirmed …)" : (matchesHead ? "(the latest change)" : "(an older change…)"))`
- `prototype/ui/ui.js:653` — `(stale ? "…unknown, not safe…" : (!matchesHead || !passed ? "…" : ""))`

A JS ternary evaluates only the selected branch, so when `stale` is truthy neither
read happens and the `!stale &&` prefix is never consulted. It has **zero observable
effect**.

Mutation **M1** removes exactly that prefix (the "bypass the `isFailureView` check"
mutation the dispatch requested) and the suite stays **green, 4/4 passed**. That is
the empirical proof of deadness, not just a reading of the control flow.

Consequence: the commit subject's central claim — "evidenceHtml downgrades current
head verification during outages" — is carried entirely by the two `stale ?`
ternaries at lines 642 and 650. Those *are* real and *are* covered (M3, M4 killed).
The `matchesHead` guard is decoration that reads as a safety interlock.

Risk if left: a later maintainer who trusts the guard and removes the two ternaries
("`matchesHead` already handles it") silently restores green badges during outages,
and the suite will not catch it.

Fix: delete the dead `!stale &&` prefix and correct the commit message / C-1426
note to name the ternaries as the mechanism. Alternatively make the verdict genuinely
depend on it (`var verdictUnknown = stale || !matchesHead || !passed;` and branch on
that), which restores the "one obvious interlock" reading and is testable.

## F2 (Medium) — a green verified-clean badge is still rendered during the outage it claims to suppress

The commit's stated purpose is that `evidenceHtml` "does not falsely show verified
green badges when head verification failed during outage". Independently of the
reviewed suite, I enumerated the live task-page DOM during a simulated 503 outage:

```
=== STATUS: /status is FAILING (HTTP 503) ===
status-error visible: True

--- ALL .badge.clean (GREEN) elements in whole task-page DOM ---
  GREEN badge text='Passed' in #evidence parent=DD
  TOTAL .badge.clean during outage = 1

--- ALL .badge.unknown elements ---
  UNKNOWN badge text='Status out of date'
  UNKNOWN badge text='Unknown'
  UNKNOWN badge text='Unknown — not safe'

--- computed style of that green badge ---
  background rgb(232, 244, 234) / color rgb(20, 87, 38)
```

`prototype/ui/style.css:108` defines `.badge.clean` with `--green-bg` / `--green-text`,
so the badge really is green on screen, not merely green-named. During an outage the
task page therefore renders a green `Passed` chip and a grey `Unknown — not safe` chip
side by side.

This is **deliberate and test-pinned**, and I want to be fair about that:
`test_04` asserts `assertIn("Passed", page.locator("#evidence .badge.clean").text_content())`
in the outage phase, and its docstring records the intent — "Historical fact
PRESERVED: Result remains 'Passed' (exit 0 did occur at tested commit)". Keeping a
true historical fact rather than erasing it is defensible, and the commit does add
the qualifiers that matter: `(live status unconfirmed · HTTP 503)` next to the tested
sha, plus the explicit `whether tests ran at the true current head is unknown, not
safe` paragraph.

My objection is narrower, and it is the visual-language one:

- `.badge.clean` is this UI's **verified-clean token**. On the index page it means
  "currently safe". Reusing it for "a run once exited 0 at a commit" overloads one
  green affordance for two different claims, one of which is exactly the
  currently-unconfirmed claim the UI exists to suppress.
- It is **inconsistent with the index policy in the same commit's own suite**:
  `test_01` requires `ZERO .badge.clean` anywhere in `.pair` during a 503 outage,
  while `test_04` tolerates one in `#evidence`. The two views apply opposite rules
  to the same token under the same outage.
- It is the first thing a 5–10 minute demo video would show.

Fix (either, ~2 lines): give the historical result a neutral class — `.badge.not_checked`
already exists at `style.css:110` — or add an explicit "at this commit" qualifier so
green stays reserved for currently-confirmed-clean. Then update the corresponding
`test_04` assertion. If the team decides the current behaviour is correct, please
record that decision in `README-UI.md` and reword the commit claim so it stops
asserting the absence of green badges, because right now the claim and the DOM
disagree.

## F3 (Low) — the repo-relative scratch change is entirely unasserted

`prototype/ui/tests/test_dom_negative_browser.py:33-36`:

```python
default_scratch = os.path.abspath(os.path.join(UI_DIR, "../../.local/scratch"))
scratch_dir = os.environ.get("TMPDIR", default_scratch)

```

Mutation **M6** reverts `default_scratch` to the old hardcoded
`/home/alexey/git/cloudflare-agent-git/.local/scratch` and the suite stays **green,
4/4 passed**. No test, and no assertion in any test, pins where the scratch directory
is or that the hardcoded machine-specific path is gone. The second half of the
commit's claimed scope is therefore unverified by its own suite.

Observations, none blocking:

- The new default resolves to the **worktree's** `.local/scratch`
  (`/home/alexey/git/agent-branches-l4/.local/scratch`), not the canonical repo's
  scratch. That is correct for a linked worktree and each worktree gets its own
  directory.
- No git pollution: `.gitignore:1` is `.local/`, and `git check-ignore -v
  .local/scratch` confirms it is ignored. Verified the directory is created and
  stays empty after a run.
- Respecting a pre-set `TMPDIR` before falling back is the right ordering, and is the
  genuinely portable part of the change.
- `os.environ["TMPDIR"] = scratch_dir` runs as a **module-import side effect**, which
  leaks into every other test module in a combined `pytest tests/` run. `setUpClass`
  is the better home for it. Low severity, but it is the kind of thing that produces
  a confusing failure in an unrelated module later.

Suggested: one assertion that `scratch_dir` is not an absolute machine-specific
literal, e.g. that it is under the repo/worktree root, which would kill M6.

## Honest limits of this review

- I reviewed one commit on one branch in a worktree. I did not review the branch's
  whole history, and I did not run the real server or a real outage — all evidence
  comes from the committed mock server plus my own probe reusing it. Real-network
  failure modes (DNS failure, hang instead of 503, an error object with no
  `message`, so that `stale.error.message` renders as `undefined`) are **not**
  covered by anything I ran. `markStale` defaults to `new Error("status fetch
  failed")` when given no error, but `refresh()` at `ui.js:802` always passes the
  fetch rejection, whose `.message` I did not probe for emptiness.
- My mutation coverage is 6 hand-chosen mutants of a 20-line change, not a mutation
  score. Two survived; a different mutant set could surface more. I claim exactly
  what the table claims.
- F2 is a judgement call about visual language and consistency, not a crash or a data
  lie. A reviewer who weights "never erase a true historical fact" above "green means
  currently confirmed" could reasonably ACCEPT with F1 and F3 fixed. I think the
  index/task inconsistency is worth resolving explicitly either way, which is why it
  is on the required list rather than in "what this gets right".
