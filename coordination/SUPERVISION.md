## Source contract

The following describes intended service behavior and retained safety rules. Verify it against the actual loaded deployment before claiming runtime acceptance.

`scripts/supervision/service.py` runs continuously as the genuinely bound `experiment-supervision` aplexer shell session. It samples `coordination/TEAM-REGISTRY.json` and `TASKS.json` plus actual session/process liveness every 60 seconds. Changed active task revisions prompt responsible principals to inspect queues, arrange head-owned execution and obtain first useful artifacts. It never launches LLM teams or repeats unchanged status requests to burn tokens. No ready work, explicit holds, blocked dependencies, quota denial and healthy compute are distinct from unexplained idle; principals must update truthful task statuses, outcomes and next actions.

Each meaningful task revision has one idempotently keyed durable envelope; timestamp-only edits do not create revisions. An unchanged queue can generate a new accountability episode after verified unexplained idle exceeds five minutes and the previous request was acknowledged. Inbox-only delivery is the default. The same envelope can be submitted by native `message deliver` only after two fresh idle/waiting observations and empty rendered composers, followed by an immediate screen recheck. Unknown, busy, multiline, feedback/menu and human draft prompts deny input. Claude's existing unsubmitted deployment draft is protected. A Codex placeholder is not a draft. Codex wake additionally requires fresh known quota with more than 15% remaining in every available window. Native readiness remains authoritative; the service never overrides it or sends Enter directly. Claude requests are sparse and event-based, at least 30 minutes apart. Unknown/uncertain delivery outcomes forbid retries. Submitted requests stay pending until a correlated genuine reply or native read ACK; transport submission is not task completion.

Receipts, identity, status, event history and errors are private under `.local/supervision/`; metrics may read these files. An ACK proves read acknowledgment only, not productive work or agreement. Principals must reply with owners/task IDs/evidence and ensure the next useful step proceeds. The service records private reply envelopes and actual sender/reply correlations, ACKs reviewed envelopes, and never executes reply text.

All operational evidence is retained losslessly. At 4 MiB the event log moves into a uniquely named gzip archive; older live receipts/replies/delivery records beyond 2048 move into the same private archive store. `archives/manifest.jsonl` records original filename, SHA-256 of original bytes, SHA-256 of compressed bytes, byte sizes and archival time. The service verifies decompressed bytes and digest, fsyncs archive and manifest, and checks the original is unchanged before removing its live duplicate. Previous archives are never overwritten or expired. Currently unresolved evidence stays live. Archived send receipts can be read back to prevent duplicate sends. This supersedes the earlier destructive rolling retention implementation; no production archive operation has been performed by the tests.

Total private supervision storage has a 128 MiB soft warning and 256 MiB hard guard, including the binary, archives and manifest. Reaching the hard limit visibly pauses native sends, delivery and ACK processing, preserves all existing data, and reports `storage.state=paused-hard-limit` in the bounded current status file. An archive whose temporary compressed copy would exceed the hard limit is also refused with the original preserved. The service does not purge data to resume; an owner must arrange safe archival capacity/export and explicitly restore available space. The metrics database and sanitized journal remain additional long-term datasets. Source changes require head-owned independently reviewed integration under the custody/provenance rules above; routine root approval is not required. This documentation correction does not reload or change any service.
