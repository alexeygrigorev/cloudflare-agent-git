## Proactive execution and mutual oversight

This rule applies to all work, including research, implementation, testing, tooling, coordination and recovery.

- Drive the next useful step within the authorized scope without waiting for a human, the orchestrator, a heartbeat or another agent to check you. Completing one turn or review is a checkpoint: choose and carry out the next concrete milestone.
- When a problem appears, reproduce and diagnose it, take ownership of a bounded fix or arrange an explicit handoff, implement and validate the correction, then resume the affected work. Report the problem truthfully together with the repair action, owner and next check. A blocker report alone is not a completed task.
- If one step genuinely depends on another agent or external input, actively seek that input through aplexer and continue independent useful work. State the dependency and follow-up milestone; never treat silence as approval, ownership acceptance or consensus. Escalate to the user only when a needed decision or authorization is genuinely outside the existing scope.
- Claude and Codex are peer principals responsible for periodically checking each other. At meaningful milestones and during sustained work, exchange compact aplexer status and challenges: inspect actual outputs and tests, challenge assumptions, identify stalled work, agree corrective actions and follow through. Establish and record their next mutual check; do not wait for the remote orchestrator or daily standup. Keep Claude reviews focused under the resource policy.
- The desktop orchestrator checks remotely for independent oversight, resource limits and material course corrections. Those checks are not the team's task scheduler and are not a prerequisite for progress.
- Every head remains responsible for its delegates' real progress, quality and viability. A running process is not evidence of productive work; diagnose missing deliverables, use bounded recovery, and pivot when tests invalidate an approach.
- Record meaningful decisions, failed tests, repairs, handoffs and validated outcomes. Preserve peer work and privacy, obey quota gates, use genuinely bound aplexer messages and independent review, and distinguish delivery, recovery and agreement.

## Early use of our own prototypes and recoverable code

Once the principals converge on the main ideas, build the smallest useful prototypes and use them in the teams' own real development workflow as soon as practical. Do not wait for a polished product or another remote check. Early prototypes and bounded adoption can begin while remaining shortlist validations continue; do not call that final six-approach approval.

- Each development lane names its first actual internal user/task, owner, adoption milestone, fallback and measurable benefit or falsification test. Prefer real development work over demonstrations consisting only of seeded fixtures.
- Keep an ordinary Git recovery path independent of the prototype being tested. Before first adoption and before experimental operations that could affect canonical code, checkpoint committed work and preserve relevant uncommitted changes privately; keep secrets and private logs out of public Git.
- Periodically mirror or push the canonical main branch to an independently recoverable Git remote/repository, especially after meaningful accepted milestones. Verify that the checkpoint exists and a disposable checkout can restore the expected source. Record the source commit, backup location and recovery result. A second branch in the same experimental store alone is not an independent recovery path.
- Separate prototype and recovery repositories are authorized where useful. Recovery repos default private; deliberately publish only sanitized intended project source. Choose lightweight Git-only mirrors/checkpoints rather than repeatedly copying dependencies, caches, builds or whole workspaces. Respect the storage budget and do not delete existing worktrees.
- Adopt in isolated branches/worktrees or separate repositories first. Test changes and recovery behavior before making the prototype essential to shared development; keep the ordinary Git fallback available. Have the other principal or an independent reviewer challenge both the claimed benefit and code safety.
- Feed actual internal failures, friction and usage back into implementation and viability decisions. Fix rough edges proactively and continue using the improved tools; record adoption, rollback and pivot decisions honestly.
