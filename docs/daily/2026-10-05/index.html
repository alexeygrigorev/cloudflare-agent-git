Day 3: Failed Pushes Stop Before They Write Twice

This corrected edition explains what the AI agents built for agents that share one repository. Agent Branches now stops instead of repeating a failed push. The team merged the dashboard but nobody tried it in a browser, and stopped agents still need a nudge. Token counts cover two sessions, and hourly numbers only sample reported status.

Alexey GrigorevWritten with Claude Opus5 October 2026
EVIDENCE UP TO 2026-10-05 08:43 UTC30 SOURCES LINKED BELOW

On October 1, Cloudflare announced a competition to build the next Git platform. I gave the research to a team of AI coding agents. Their question is what Git-like tools coding agents need. When several agents change one project at the same time, their changes clash, and the extra copies of the project fill my disk.

Correction, drafted October 5 at 10:40 Berlin time. The first version of this post went out at 09:19 Berlin time. Its title and conclusion leaned on speed: plain Git finished one task in 0.44 seconds, Agent Branches in 0.99. But I want better Git for agents working at the same time, not faster Git. The first version also held back numbers we could already publish. This version adds them, explains each product, and fixes several details. The final publication time goes into the page metadata when it's released.

The report covers 09:00 Berlin time on October 4 to 09:00 on October 5, which is 07:00 to 07:00 UTC. I read sources up to 08:31 UTC on October 5, and I give the time of every finding after the window.

The problems behind "better Git"

Agents that change code at the same time need to coordinate before merging, avoid duplicate work and recover from conflicts. Work should also move between computers and keep going when one agent stops.

On October 4 I asked the agents to form teams around these problems. A Gemini-based agent leads Agent Branches, an agent on a z.ai model leads the dashboard, and Grok agents lead the launcher and the messaging product. Codex, one of the two original lead agents, watches all four teams.

The four teams cover code changes, visibility, launch decisions and messages between computers. The full-size team map shows an earlier plan. Its pending dashboard label predates the dashboard merge, so it doesn't show current delivery status.

Agent Branches

Agent Branches gives each task its own fork of the repository. A task holds a time-limited lock on what it may write. The fork accepts an ordinary Git push, and the server records who did what.

The Gemini team's most useful change handles pushes that fail. If the server refused a push, returned an error or timed out, the software used to resend it. Sometimes the first push had already arrived, which meant a duplicate. Now it stops and reports which changes went through, which didn't, which are unknown and which it never tried. A person can check before anything gets written twice.

An agent on a z.ai model reviewed the change and ran 61 tests. In one test, the server saves the change and then drops the connection, and the push still goes out exactly once. The reviewer accepted it for this narrow case, with a few notes on the documentation.

They also built one real feature twice, adding link listing and visit counters to a small link shortener. One copy used a Git worktree, which is a second working folder of the same repository. The other used Agent Branches.

Both versions came out identical and passed 14 tests, and a separate reviewer repeated the trial and accepted it. But that's one internal trial with one agent, not proof anyone else wants the tool. It's also the only feature in the selected consumer acceptance export for this window, so it isn't a count of everything built.

The trial found four problems in the tool:

  • The client looked for the fork's remote address at the top level of the server's answer, but the server puts it one level deeper.
  • The client has to normalize two names for the task identifier returned by the API. That mismatch needs a consistent client interface.
  • State saved by one run can leak into the next.
  • The access token sits in the repository's own Git config, readable only by its owner. That protects the stored config, but doesn't prove every invocation hides credentials.

The team already fixed the last item, and the first three still need work.

An earlier trial seemed to show Agent Branches catching a broken combination that Git missed. But it tested Git only after merging. The team's corrected report shows that Git with the same tests before merging catches the same bug. So early warnings haven't shown an advantage yet.

Next, the Gemini team wants two real coding agents doing real work at the same time. Both setups get the same checks before merging, and plain Git stays available as a fallback.

The dashboard

The dashboard counts agents, hours and tokens per product. It merges overlapping work periods so nothing gets counted twice, and it keeps unknown values as unknown instead of zero. The team merged it into the main branch with a server and a view for each of the four products.

The adoption review read the code and ran 48 tests, but nobody opened the dashboard in a browser. A Grok agent's review found hidden usage that belonged to no product and two different end times in one report. Some numbers also didn't say where they came from.

A separate patch was accepted at 06:10 UTC in the task ledger. A newer version addressing unassigned usage and window labels was reviewed after 07:00 UTC, outside this reporting window. Those are different versions, and neither review proves the newer patch reached the main branch or a browser.

The dashboard produced the hourly numbers in this report, and it still misses agents that don't report their status. Next, the dashboard team fixes the end times, gets an exact review of the merged code, and checks it in a browser.

The launcher

The launcher decides which agent to start.

Its written launch rules go like this:

  • It reads fresh quota before each launch, and an unknown reading or an error means no launch.
  • It never starts Codex at 15% remaining or less.
  • It checks that the task fits the agent before choosing, and only gives extra weight to soon-resetting quota among agents that already qualify.
  • A new worker gets at most 1,500 MiB of memory, and the server keeps 10 GiB of memory and 50 GB of disk free.
  • A task's scratch files stay under 512 MiB, and nothing new goes into the temporary folder while it's below the floor.

The team doesn't compile Rust code, make purchases, redeem quota resets or run agents in the cloud.

In the reporting window, the launcher started two Grok reviews of the dashboard. The first stopped at its 300-second limit with no accepted output. The second finished at 05:50 UTC after 464 seconds and produced a 25 KB review. The record names Grok but not the model version.

Earlier reviews found that the launcher could skip its own lock checks. A worker also picked up its lead's identity through a fallback, and the newer guard against that doesn't fully separate them yet. A script started both runs, so they don't show agents working on their own. Next, the launcher team wants a worker with its own identity to finish a useful review and to record retries reliably.

Messages between two computers

The messaging team connected my Windows desktop and rented Linux server over SSH. The desktop dials out, so it needs no open ports. Each message has an identifier that its reply refers to, and the system records reading a message separately from finishing the task.

Their report shows a task sent at 01:39 UTC, read by the desktop at 01:57, with the reply confirmed at 02:00. Joining the desktop to the system took 1,415 milliseconds, and sending the reply took 974. Most of the 18-minute wait came from the desktop checking for messages on a timer.

A Python script drove the exchange and someone checked for replies by hand. Nobody has tested Windows text handling or recovery after going offline yet.

Later, at 07:11 UTC, a worker on the message bus read a task and sent back a Grok review with the correct reply link. Nobody has acknowledged or accepted that reply yet. Next, the messaging team wants delivery in both directions, retries after a computer comes back online, and real model work through the bus.

Headless workers and interactive leads

After the reporting window, the teams used the existing message systems for real work. A headless Grok worker read a task, confirmed receipt and returned a capacity-error review. Its lead acknowledged the reply. The corrected report executor and its independent reviewer also exchange native Aplexer messages with the interactive publication lead.

These are real mixed headless and interactive exchanges. The separate agent-bus project has a durable authenticated Python command line, but no independently accepted unified adapter joins it to every interactive agent. The Gemini integration lead owns that adapter and restart handling. Two useful tasks starting automatically after earlier work finishes remain unproven.

Agents that stop

On October 4 I asked the agents to keep working when a lead agent stops. That still fails, because overnight, at 04:28 and 06:48 UTC, work resumed only after another agent nudged it.

The Gemini runtime team made the first fix in the window. The service that wakes agents skipped the product projects. The team repaired how it finds projects and their aliases, then added tests and had it reviewed.

After the window, a Grok agent studied one likely cause. When the model provider is at capacity, the agent stops. Its status has no hook for errors, so it can keep saying "working". That matches the stale status we saw, but no recorded incident proves it's the cause every time.

The wake-up service also looks for the word "Select" to spot a menu, and "Selected model is at capacity" matches it by mistake. The agent proposed a 180-second rule and tested it in a dry run with 20 tests. Nobody installed it, and it still has known defects.

Any fix has to keep the existing protections. It can't fake an agent's status or type into its window. It also can't overwrite an unfinished draft, and Rust builds stay on hold.

At 08:05 UTC the wake-up service sent a status request to Codex, the agent that watches all teams. Codex replied at 08:06, and the service confirmed it at 08:06:37. A message going both ways works, but no task came out of it. At 08:22 UTC the service reported no errors, which shows it runs, not that work resumes.

My test is still two useful tasks that start when earlier work finishes, with nobody nudging, and that hasn't happened. The Gemini runtime team owns the next small fix, and Codex reviews it.

The numbers

The collector stored token counts for two sessions on a Muse Spark model, run through OpenCode, a coding agent tool:

  • Dashboard: one session building the views, 23 messages and 680,764 tokens in total. That splits into 80,965 input, 585,767 cache reads, 11,404 output and 2,628 reasoning.
  • Messaging: one session reviewing the bus, 14 messages and 406,080 tokens. That splits into 46,640 input, 350,638 cache reads, 5,335 output and 3,467 reasoning.

Together that's 37 messages and 1,086,844 tokens as counted by the provider. An independent reviewer checked all 37 records: each has numeric usage fields, and each records zero tokens written to cache. The provider reports input, cache reads, output and reasoning separately here. We haven't established a portable non-cache input definition across providers.

These are two sessions, not whole products. The collector doesn't record Grok, z.ai or Gemini agents, so Agent Branches and launcher tokens are unknown, not zero. Token counts don't show money spent.

The five-dollar limit

My Cloudflare budget is $5 a month in total, including the plan I already pay for. So the agents checked how Cloudflare bills Durable Objects, its small always-addressable servers.

Cloudflare's Durable Objects pricing, which the agents checked today, charges for duration in gigabyte-seconds. You multiply reserved memory by the seconds an object stays active, and message size doesn't matter. Every object counts as 128 MB, or 0.128 GB, whatever it actually uses.

The plan includes 400,000 gigabyte-seconds a month. Above that, Cloudflare rounds up to the next million and charges $12.50 per million. When an idle object hibernates, meaning Cloudflare puts it to sleep under its conditions, Cloudflare doesn't charge for that time.

Two objects that never sleep for 30 days come to 663,552 gigabyte-seconds. That's 263,552 above the allowance, which rounds up to a million and adds $12.50. With the $5 plan, the bill reaches $17.50 before requests, storage or other charges.

That's an example, not a bill and not the price of messaging. A short-lived relay that hibernates would stay active for far less time. An earlier figure of $8.29 forgot the rounding, and the team withdrew it.

Running model agents needs compute and model capacity. A relay only moves messages. This project uses the existing rented server and model subscriptions for execution, and this report has no measured incremental execution bill. The Cloudflare example covers relay duration only. It doesn't price running agents.

The agents recommend the simplest path: keep SSH with a local queue that stores messages on disk. It only needs to hold pending messages for offline computers, retries, duplicate checks and read confirmations, not every agent's history. Nobody knows how much the rest of my account already uses or whether I can cap overage. So the cloud relay stays on hold, with no new paid service, no agents in the cloud and no purchase.

For agents that stop, the test is two useful tasks that start with nobody nudging.
